# تقرير تثبيت حالة المهمة 02 — إعداد Flutter وAndroid

**تاريخ الحالة والتدقيق:** 2026-11-19  
**الحالة:** المهمة 02 مفتوحة ومتوقفة عند بوابة توفر بيئة بناء واختبار موثوقة. لم يبدأ العمل في المهمة 03، ولم تتغير المعمارية أو الخطة المرجعية.

## ما أُنجز والتحقق المحلي

المضيف Ubuntu 24.04 بمعمارية `aarch64`/ARM64. أظهر `sdkmanager --list_installed` أن حزم Android SDK المحددة مثبتة:

- `platforms;android-36`، revision 2، في `/home/ubuntu/Android/Sdk/platforms/android-36`.
- `build-tools;36.1.0` في `/home/ubuntu/Android/Sdk/build-tools/36.1.0`.
- `platform-tools`، revision 37.0.3، في `/home/ubuntu/Android/Sdk/platform-tools`.

تتفق إصدارات `source.properties` وبيانات `package.xml` مع قائمة `sdkmanager`. ملف `android.jar` موجود واجتاز `unzip -t` دون أخطاء. سُجلت بصمات SHA-256 لملفات رئيسية كلقطة محلية للمقارنة المستقبلية؛ هذه البصمات لا تمثل تحققًا مستقلًا من مطابقة الملفات المستخرجة لبصمات أرشيفات Google الرسمية.

```text
android.jar  d9eb9da824d9e247a352f570f01e1169e725b2954bca9e283a71786c59b59f9a
aapt        06f1e01b791bc46fdeb230e4a4bd2731d51791956cdde33db7f63a50c8d8cc94
aapt2       012764928a2e5ad747531f669fcda1cf2ccd2d0b6eb8bdb728807c17e3cf16d0
adb         7c8042370cb04ad0f6ead179174d8cc52f119ffbcafdefe6db9a4db49b731f95
```

قُبل `android-sdk-license` وحده بعد موافقة المستخدم؛ سبعة تراخيص أخرى ما زالت غير مقبولة. هذه الموافقة تخص Sandbox الحالية ولا تمتد تلقائيًا إلى runner خارجي. أظهر `file` أن `adb` و`aapt` و`aapt2` ملفات Linux ELF x86-64. لم تُشغّل على ARM64، ولذلك فالتثبيت الفعلي لا يعني أن أدواتها التنفيذية قابلة للتشغيل على هذا المضيف.

Java OpenJDK `21.0.12.1` مثبتة وتعمل على AArch64. Flutter وDart وGradle وKotlin compiler غير متاحة على `PATH`. وثيقة فحص manifests الرسمية تسجل أن Flutter Stable 3.50.0 يوفر سجل Linux x64 فقط ولا يوفر Linux ARM64؛ التفاصيل وروابط الأرشيفات والبصمات في [توثيق دعم Flutter على Linux ARM64](FLUTTER_LINUX_ARM64_SUPPORT.md). [1]

## ما تعذر تنفيذه ومراجعة Kotlin/Gradle

لم يعثر الفحص على `pubspec.yaml` أو `android/gradlew` أو `gradle-wrapper.properties` أو ملفات Gradle (`build.gradle` و`settings.gradle`) أو ملفات Kotlin (`*.kt` و`*.kts`). لذلك لا توجد إعدادات Kotlin أو Gradle فعلية خاصة بالمشروع لمراجعتها أو إصدارات معتمدة يمكن تسجيلها. لم يُنشأ scaffold، ولم تُنفذ `flutter doctor` أو `flutter analyze` أو `flutter test` أو Gradle أو Kotlin أو بناء APK.

توضح وثيقة Flutter أن موضع إعداد Kotlin في قوالب Android الحديثة قد يكون في `android/settings.gradle`. وتذكر وثيقتها حدًا أدنى تاريخيًا لـ Kotlin Gradle Plugin، لكنه ليس أساسًا كافيًا لاختيار إصدار TeleManager قبل إنشاء القالب ومراجعة متطلباته. [7] للمقارنة العامة فقط، يذكر جدول Gradle أن تشغيل Gradle على Java 21 يتطلب Gradle 8.5 أو أحدث، واستخدام Java 21 كـ toolchain يتطلب Gradle 8.4 أو أحدث. [8] وتعرض وثائق Android توافق AGP 9.5.0 مع Gradle 9.6.0 كحد أدنى وJDK 17. [9] هذه حدود توافق وليست توصية باختيار تلك الإصدارات للمشروع. تُحدد النسخ بعد إنشاء scaffold رسمي بإصدار Flutter المختار ومراجعة إعداداته.

## المراجعة الساكنة لـ `setup_toolchain.sh`

لم يُشغّل السكربت في جولة التدقيق؛ تمت مراجعة نصه فقط لأن بدايته تنفذ أوامر تثبيت نظام وقد تنزّل أدوات.

على ARM64 ينفذ السكربت `apt-get update` ويثبت متطلبات النظام (`curl`, `git`, `unzip`, `xz-utils`, `zip`, `libglu1-mesa`). ثم يتحقق من وجود Android Command-line Tools، وإذا لم يجد `sdkmanager` ينزّل الحزمة الرسمية المحددة ويتحقق من SHA-256 ويفكها. بعد فحص `uname -m` يطبع رسالة العائق ويخرج بالرمز `2` عند `aarch64` أو `arm64`.

بسبب هذا الخروج المبكر، لا يقرأ السكربت manifest Flutter على ARM64 ولا ينزل Flutter أو يثبته. كما لا يصل إلى كتابة `ANDROID_HOME` و`ANDROID_SDK_ROOT` وPATH في `.bashrc` أو إلى `flutter --version`. لا يثبت حزم Android Platform أو Build-Tools أو Platform-Tools، ولا يقبل تراخيص SDK، ولا ينشئ مشروعًا أو ينفذ تحليلًا أو اختبارات أو APK. لذلك تشغيله على ARM64 **لا يكمل إعداد Android أو Flutter**. لم يُشغّل في هذا التدقيق منعًا لأي تثبيت إضافي.

على Linux x86-64 يختار السكربت أحدث Flutter stable وقت التشغيل من manifest الرسمي، ويتحقق من SHA-256 ثم يثبت Flutter إذا لم يكن موجودًا؛ كما يكتب مسارات Flutter وCommand-line Tools وPlatform-Tools في `.bashrc` ويشغّل `flutter --version`. لكنه لا يثبت حزم Android المستهدفة أو Build-Tools أو Platform-Tools، ولا يقبل التراخيص، ولا ينشئ scaffold أو يشغّل التحليل والاختبارات أو يبني APK. اختيار Flutter فيه غير مثبت على إصدار محدد للمشروع، بل يتبع stable المشار إليه في manifest وقت التشغيل.

## حالة Git

المستودع المحلي مهيأ (`git rev-parse --is-inside-work-tree` يعيد true)، لكن لا يوجد `HEAD` أو commit، ولا يعرض `git remote -v` أي remote. الملفات الحالية غير متتبعة بعد. لم يُنشأ مستودع GitHub أو workflow؛ لذلك لا توجد نسخة ملتزمة على GitHub لتشغيل Actions عليها.

## GitHub Actions

GitHub Actions خيار محتمل لبناء Flutter Android خارج Sandbox، لكنه دراسة فقط. توضح وثائق GitHub أن ملفات workflow توضع في `.github/workflows`، وأن كل job يحدد runner. [4] الخيار الأقرب عند الإعداد هو `ubuntu-24.04` x64، المتوافق مع سجل Flutter Linux الرسمي الذي فُحص. [1] [2]

تختلف موارد runner والتكلفة بحسب ما إذا كان المستودع عامًا أو خاصًا وخطة GitHub؛ يجب التحقق منها قبل التفعيل. [2] [3] المتطلبات تشمل مستودعًا وشيفرة ملتزمة، وتثبيت إصدارات الأدوات بما يتوافق مع scaffold، وموافقة منفصلة قبل قبول تراخيص Android SDK على runner خارجي، ثم تشغيل التحليل والاختبارات وبناء debug وحفظ APK كـ artifact. لا يحتاج debug إلى مفاتيح نشر؛ وأي توقيع release أو نشر يحتاج أسرارًا وموافقة مستقلة. ينبغي تقييد صلاحيات `GITHUB_TOKEN` وتثبيت actions الخارجية على SHA كامل أو lockfile موثوق. [10]

لم يُنشأ remote أو workflow، ولم تُقبل تراخيص على runner خارجي، ولم يُشغّل أي build.
