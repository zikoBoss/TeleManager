# TeleManager — المعمارية

## الحالة
هذه وثيقة تأسيسية مشتقة من `MASTER_BLUEPRINT.md`. المستودع في مرحلة التأسيس؛ لا توجد بعد تطبيقات فعلية للمحركات ولا تكامل TDLib ولا قاعدة بيانات. لا تُعامل الرسوم أو العقود المقترحة على أنها ميزات منفذة.

## الهدف
مدير ملفات افتراضي سحابي، لا واجهة Telegram. الهاتف يحتفظ بالبيانات الوصفية وCache محدود، ويظل منطق إدارة الملفات مستقلًا عن مزود التخزين. Telegram/TDLib هو المزود الأول فقط.

## حدود الوحدات
- **TM-Core:** نموذج الملفات والمجلدات، VFS، التصنيف والبحث والوسوم والمفضلة. لا يعتمد على Android أو TDLib أو أي مزود.
- **TM-Cloud:** عقود التخزين الموحدة، قدرات الحساب، نتائج المزود والأخطاء. يعتمد عليه منسق العمليات، وينفذه TelegramProvider.
- **TelegramProvider:** المصادقة والرفع والتنزيل والحذف واسترجاع بيانات التخزين عبر TDLib. لا يصل مباشرة إلى Widgets أو TM-Core.
- **TM-Transfer:** طابور دائم للرفع والتنزيل، التقدم والإلغاء والاستعادة والمحاولات وحدود التزامن.
- **TM-Cache:** Cache وthumbnail وOffline وسياسات المساحة. لا يحذف أي أصل سحابي.
- **TM-Backup:** snapshot متسق ومشفّر ومتحقق منه، ثم استعادة وترحيل.
- **TM-Sync:** سجل تغييرات متعدد الأجهزة، idempotency والتعارضات وtombstones.
- **TM-UI:** Flutter presentation فقط. يستدعي طبقة التطبيق/المستودعات ولا يحتوي منطق TDLib أو SQL.
- **Android bridge:** Kotlin/NDK boundary محتمل لـ TDLib؛ الاختيار مؤجل حتى تقييم المكتبة والـABI والتراخيص والبناء.
- **Data:** SQLite عبر Drift، مخططات ومهاجرات ومستودعات؛ DB محلية لبيانات TeleManager وليست قاعدة TDLib.

## تدفق مقترح
`TM-UI → Application/Use Cases → TM-Core + TM-Transfer → TM-Cloud → TelegramProvider → TDLib`

يتعامل TM-Core مع معرفات TeleManager الداخلية UUID. المراجع الخاصة بالمزود محفوظة منفصلة في `storage_objects` ويمكن تحديثها؛ لا يكون message_id مفتاحًا داخليًا.

## بنية المجلدات
المجلدات الحالية تعكس الأقسام المقترحة في المخطط: `lib/core`, `lib/data`, `lib/engines`, `lib/providers`, `lib/features`, `lib/shared`, `android/native/tdlib_bridge`, `assets`, `test`, و`docs`. تُضاف الملفات التنفيذية تدريجيًا بعد اختيار الأدوات والتحقق من البيئة.

## بوابات التنفيذ
1. تأسيس المستودع والوثائق والقواعد.
2. تجهيز Flutter/Android وأخذ قرار اعتماديات مبرر.
3. بناء تجربة مستقلة لتقييم TDLib، بما يشمل المصدر والترخيص والإصدارات وABI والتوافق.
4. لا يبدأ تكامل المصادقة والرفع والتنزيل قبل نجاح/توثيق بوابة TDLib.
5. بعد إثبات المزود: VFS/قاعدة البيانات والعمليات والطابور وفق ترتيب roadmap، ثم الواجهة النهائية والمعاينة والمزامنة والنسخ.

## قرارات مؤجلة
- إصدار Flutter/Dart/AGP/Kotlin/NDK وABI.
- مكتبة/حزمة TDLib وطريقة الربط.
- إصدارات Drift وRiverpod وGoRouter وحزم التشفير.
- سياسة نسخ القناة وربطها بالحساب وآلية metadata السحابية.
- الحد الفعلي للملف وحجم الأجزاء وقابلية الاستئناف بعد الاختبار.
- استراتيجية مزامنة وتعارضات التنفيذية.

لا تثبت قرارات مؤجلة أو أرقام حدود في الشيفرة من دون فحص الوثائق الرسمية وتجربة قابلة لإعادة الإنتاج.
